# 代码结构与流畅度审查（2026-11-01）

## 依赖结构

- 扫描 `src` 与 `electron` 的静态模块依赖：没有循环依赖。`npm run check` 现在会在每次检查时重新验证模块图，防止循环依赖回归。
- `src/app.js` 有 72 条导入，是当前的组合入口。它把大量控制器通过回调互相连接；这不会形成模块循环，但使一次状态变更容易触发多个视图的更新。
- `src/model.js` 仍是较大的领域入口。原来有 17 个模块直接从 `src/render/webgl-renderer.js` 获取 UV、组变换和面状态工具。现已把这些纯函数移至 `src/common/core/geometry-utils.js`，控制器直接从那里导入。WebGL 模块仅由应用入口和模型截图模块直接引用；检查脚本会阻止其他模块重新依赖它。
- 大文件集中在 `webgl-renderer.js`（约 3355 行）、`model.js`（约 2354 行）和 `events-controller.js`（约 1349 行）。大小本身不直接导致掉帧，但增加了缓存失效和状态同步的排查难度。

## 撤销与截图中的报错

截图的「贴图还原校验失败」来自分层贴图还原：图层组没有 `source` 属性，旧逻辑却给它补上 `source: null`，导致还原后的贴图哈希与日志不符。现在贴图差异记录属性是否存在，并兼容没有这项记录的旧图层组差异。

使用实际报错的项目文件夹的工作副本回放：旧代码在第 1510 次操作撤销时复现相同的贴图 ID 校验错误；修复版从该状态连续撤销 30 次通过。原始项目文件夹未改动。

此前每次撤销都从磁盘读取目标状态的全部 Cube 快照，还会在校验后再读取一遍。现在最近状态使用内存快取；重开软件后的首次撤销可以从当前状态加上受影响的快照重建。被改动的快照仍会在切换前从磁盘读取并校验。500 个 Cube、只编辑一个 Cube 的本机基准中，日记账撤销从约 432 ms 降到约 83 ms；这不包括编辑器绘制时间。

## 主视图流畅度

- 单纯移动视角时，主场景的静态几何有快取，通常不会重算每个 Cube 的 mesh。持续掉帧不能直接归因于全量几何重建；GPU 绘制、预览视图以及屏幕叠加层仍需在实际模型上分别测量。
- 之前选中对称修改器时，提示线的每一段都生成独立 SVG 节点，并且每帧重新写入 DOM。径向或曼陀罗份数高时，这属于明确的 CPU/布局热路径。现在把同色、同透明度的线段合并为路径，并复用没有变化的标记。
- 编辑模式下，撤销影响不超过 16 个节点、受影响元素不超过 64 个且没有增删、尺寸或拓扑变化时，只更新已有 GPU mesh 的对应区段。适用于 Cube、Shape、曲线和组内元素；结构变化、绘画模式或大批量操作仍走完整重建。
- 参考图在视角移动时不再反复调整 DOM 顺序或重复写入未变化的尺寸；对称辅助线按样式合并为少量 SVG 路径，减少每帧 DOM 工作。
- UV 预览开启自动旋转后会持续独立渲染；它会增加总绘制负载，但没有实机 GPU 计时数据，不能据此断定它是当前模型掉帧的主要原因。

## 后续结构工作

大量 Cube 或 Shape 同时变化时，当前仍会全量重建。要进一步定位剩余掉帧，需要在目标机器上分别测量主视图 GPU 时间、UV 预览绘制时间和编辑器主线程时间；目前没有足够证据把所有持续卡顿归因于单一环节。

## 2026-11-03：周期停顿排查与自动基准

用户的记录中，场景 CPU 和 GPU 通常只有几毫秒，但滑鼠事件与原生游标 IPC 会同时中断约 100–180 ms。仅减少模型绘制工作不足以解释或解决这一现象。本轮进行了以下修改：

- 项目记录的初始化、快照计算、读写、撤销、恢复、历史整理及归档移入独立 Worker。窗口主线程保留 IPC、项目所有权和原有逐项目操作队列；收到完成消息后才确认操作。磁盘格式、原子写入、校验和恢复规则沿用原实现。
- 手柄 SVG 保留节点并更新坐标、路径和深度顺序，避免逐帧销毁整棵 DOM。曲线标记、拖动辅助线和顶点捕捉仍保持原先的绘制层次。纯视觉叠加层从辅助功能树中隐藏，工具栏、数值属性及层级列表继续提供对应入口。
- 常规相机拖动不再查询原生游标。短时性能采样中的原生查询仅用于量测，不向相机注入可能过期的坐标。
- 性能记录增加真实 rAF 回调间隔、最大值、超过 40 ms 的次数、窗口主线程 CPU 时间、主程序中的进行中操作与事件循环延迟。`cpuMs` 是整个主进程所有线程的累计 CPU 时间；判断窗口线程应看 `threadCpuMs`，不可混用。连续采样会重新初始化计时基准，避免把两次采样之间的空闲算作卡顿。

自动基准使用 `scripts/profile-viewport-input.cjs`。它创建临时用户目录和生成模型，不打开实际工作项目；默认隐藏测试窗口。输入由 Electron 内部发送，记录保存在指定的 JSON 中。示例：

```powershell
.\node_modules\electron\dist\electron.exe scripts/profile-viewport-input.cjs --cubes=1000 --tool=rotate --duration=15000 --settle=true --accessibility=on --output=build/performance/report.json
```

`--background-cubes=1000` 会在另一个临时项目里持续批量保存；`--scene=curve` 测试曲线节点；`--trace=true` 同时输出 Chromium 内部追踪。测试会检查拖动全程有效，发生运行错误或没有进入相机拖动时返回失败。

本机样本（Electron 38.8.6 / Chromium 140；先预热，稳定场景等待初始保存完成）：

| 场景 | 时长 | 相机间隔 P99 | 最大相机间隔 | 超过 40 ms |
| --- | ---: | ---: | ---: | ---: |
| 1000 Cube，旋转手柄，初始保存完成 | 15 s | 17.1 ms | 19.6 ms | 0 |
| 一个 Cube，后台项目持续保存 1000 Cube | 30 s | 34.9 ms | 55.1 ms | 8 |
| 三维曲线节点，旋转手柄，开启内部追踪 | 30 s | 17.4 ms | 29.5 ms | 0 |

后台压力场景的主线程 CPU 为 1531 ms / 30 s；进程累计 CPU 为 37265 ms，其中包含工作线程及文件系统工作。最后一轮曲线追踪没有超过 40 ms 的窗口主线程或渲染主线程长任务，也没有运行错误。一次较早的曲线采样出现过最大约 400 ms 的长任务，后续 8 秒和 30 秒追踪未复现，保留原报告供后续对比。

这些测试未重现固定半秒一次的停顿，但内部注入输入绕过了物理滑鼠到 Windows 的路径，因此不能据此宣称已验证所有硬件输入情形。测试结果证明的是上述场景和当前代码路径；此前用户记录中的原生输入停顿仍需结合实际运行数据判断。

工作线程的撤销、重做、UUID、归档恢复、错误回传已加入回归测试，并验证了 ASAR 打包后可正常启动工作线程。收尾检查通过：165 个源码文件及模块依赖图、62 项记录与撤销测试、模块和渲染回归测试。
