# CubeBricks 全流程效能優化提案

本文件基於 2026-11-01 的原始碼審視，記錄已落地的優化及後續提案。尚未實作的條目不代表已測得加速倍數。目前已有靜態 mesh 快取、局部 GPU buffer 更新、貼圖圖集局部上傳、圖層髒區合成、元素列表虛擬捲動與日誌近期快取；以下方案保留並擴展這些機制。靜態模組依賴檢查已存在，未見循環引用；較大的結構風險是狀態更動透過回調導致多個消費端重算。

## 實施進度（2026-11-02）

### 主視圖逐幀審查與結構整理（2026-11-03）

- 六向輪盤在視角方向不變時跳過 DOM 重寫；空選取的手柄與沒有參考圖、Locator、鏡像提示的疊層走空場景快路徑。同一主視圖影格共用畫布尺寸，避免疊層更新後重複觸發版面計算。
- Java／基岩格式的尺寸約束框改為資料變更才重新上傳；WebGL 繪製沿用未變的矩陣、材質參數和頂點配置。這些處理降低單 Cube 場景的固定提交成本。
- 後續逐幀檢查發現：空參考圖仍先讀容器尺寸才走空場景快路徑；UV 預覽未啟用自轉時仍先讀視窗邊界才判斷不用動畫。兩者都已把便宜的狀態判斷移到版面讀取之前。底部參考網格的三組線已有逐頂點顏色，現合併為一次繪製；吸附精度或格式變更時才重傳。
- 鏡頭平移或縮放不改變半透明面的相對深度順序，因此沿用既有面序；鏡頭轉動仍檢查排序。繪畫爆炸視圖的修改器批次按幾何與選取版本快取；無動畫時跳過 Cube 進出場列表處理，無修改器時跳過實例分組。大量選中項的排除頂點範圍按幾何與鎖定／出生狀態快取。
- 幾何中心、選框和螢幕邊界改為單次遍歷，不再為各軸複製頂點陣列。局部撤銷的面更新增加按原始面順序排列的 UID 索引，只取受影響的 Cube 面；原始順序與貼圖對應保持不變。
- 半透明面按鏡頭深度排序時，先用一次線性檢查判斷既有順序是否仍有效；共面深度相等保留穩定順序，不再因此每幀重新排序和上傳。真正交叉時每面只計算一次深度，再穩定排序。新增共面多面與實際繪製快取的回歸測試。
- 把面拾取 BVH、半透明面序和 GLSL 程式碼拆到 `src/render/face-bvh.js`、`src/render/face-order.js`、`src/render/shaders.js`；渲染器保留原有對外匯出。模組圖檢查未發現循環引用。BVH 局部重設按建立時保存的節點深度排序，不再在比較過程反覆沿父鏈計深度。
- 仍須在實際卡頓專案比較 `scene.frameInterval`、`scene.totalCpu` 與 `scene.gpu` 的 P95。若 GPU 時間偏高，下一步優先處理虛化修改器結果的整場景重畫及大量修改器實例的繪製批次；若 CPU 時間偏高，先按疊層分段與透明面排序結果定位。此處未以降低拖動時畫質作為預設解法。

### 讀檔、撤銷、圖層及畫筆熱路徑（2026-11-02）

- 日誌初始化、提交、切換、驗證、打包與解包的獨立檔案採有限併發讀寫。解包先建立目錄，再寫快照，最後寫 `current_state`；只有狀態檔完成後才視為可恢復。Windows 的共同父目錄預先建立，避免並行建立時的 `EPERM`。打包進度約每 1% 或 100 ms 回報一次。
- 用提供的 `鸚鵡螺115.cbmodel` 唯讀解包並在暫存工作目錄做實測：3442 個檔案，工作副本建立約 4 秒，進度通知 100 次。這是單次暖快取觀察，尚未做同環境 A/B，不能視為固定加速倍率。
- 撤銷日誌現在回報貼圖是否改變。純幾何撤銷沿用現有貼圖資產與 GPU 圖集；貼圖、圖層或貼圖分組改動仍恢復完整貼圖。局部幾何提交在面數不變時保留面索引，只重設受影響的 BVH 條目。面拾取 BVH 的包圍盒只遍歷頂點一次；射線查找直接比較左右子節點，減少每條射線的臨時陣列與排序。
- 首頁先讀項目文字索引，封面只在卡片進入可見區域時載入；外部 Shape 包載入與首頁顯示並行。未使用的 UV 預覽不再跟主圖集一起上傳 GPU 紋理。
- 平鋪貼圖衍生圖集區域建立來源 UID 反向索引；一般貼圖筆畫不再每次掃描整張圖集尋找可能的平鋪區域。
- 螢幕空間畫筆快取同一次命中的面、UV 投影範圍與筆刷覆蓋率；同一可見畫面內的多個筆刷採樣合併成一次圖集上傳，並在同一幀繪製主視圖；二維與三維筆畫鬆手提交最終貼圖時取消同一筆尚未上傳的預覽補丁，避免重複上傳或覆蓋最終結果；調色值不再逐像素解析十六進位字串。圖層樹及後代查找使用父子索引，普通來源覆蓋的巢狀組直接順序合成，避免額外的組畫布；帶遮罩、疊色或組透明度的組維持隔離合成。模板矩形評分減少臨時物件。修改器重複 Cube 鍵值保留原有五位小數判定，減少每個頂點的暫存陣列；實例來源 UID 改集合查找。
- 日誌 58 項、渲染／繪畫、模型、圖層及來源檢查通過。這些改動只消除重複工作，未完成記憶體撤銷、穩定圖集配置與完整的局部失效依賴圖；仍須在使用者的大型場景量測拖動視角和連續畫筆的 P95。

### 分段效能量測

已加入預設關閉的短期量測：在開發工具中執行 `cubeBricksPerf.enabled = true`，操作主視圖與畫筆後執行 `cubeBricksPerf.summary()`，可取得最近 180 次的 P50／P95／P99；`cubeBricksPerf.reset()` 清除樣本。項目包括主視圖 WebGL 指令提交 CPU 時間、DOM 疊加、UV 預覽、圖層合成、圖集上傳和衍生平鋪區域。有 `EXT_disjoint_timer_query` 時，另外顯示 `scene.gpu`，它才是 GPU 執行時間；無擴充時不回報此項。這份診斷用於判斷卡頓落在 CPU、GPU 還是額外預覽，不代表已完成剩餘的渲染架構重構。
另有僅在快取失效時出現的 `scene.geometryRebuild`、`scene.selectionRebuild`、`scene.modifierRebuild`；若單純拖視角也不斷出現這幾項，表示失效路徑仍有錯誤。

撤銷另記錄 `journal.queue`、`journal.waitPending`、`journal.diskCheckout`、`journal.parse`、`journal.hydrate`、`journal.render`，以分開磁碟交易和主執行緒還原。單 Cube 還原會沿用內容雜湊未變的元素物件；層級結構及可見標籤未變時也保留元素列表的可見 DOM。對 `鸚鵡螺115.cbmodel` 的一次唯讀測量，完整模型建立約 9.9 ms，單 Cube 還原模型建立約 0.9 ms；這不是整次撤銷延遲。日誌的 locator 與 branch 獨立檔同步寫入，崩潰標記保持到兩者完成。貼圖指紋快取改按位元組數限制，避免多貼圖專案超過原本 16 項後反覆解碼。日誌完整測試 59 項通過。

半透明模型的視角拖動原本每幀對靜態面與完整面序各排序一次，面區分開啟時還每個 pass 重建頂點陣列及上傳。現在先線性檢查上幀面序是否仍正確；只有深度次序變動才重新篩選與排序。排序結果不變時沿用專用 GPU buffer，同一幀的紋理與面區分 pass 共用它。幾何局部更新會清掉這份快取，Cube 出生動畫結束後也會重新納入暫時排除的面。渲染測試與原始碼檢查通過，實機 FPS 仍待量測。

色階映射圖層原本對每次小範圍合成都重新建立 256 格顏色對照表；現在每組設定快取對照表，原地修改色卡後依設定內容失效。局部圖層合成仍只處理髒區，色階、蒙版與混合效果不變。
按色相／明度／飽和度／灰度混合時，同一塊區域內重複的上下層顏色對共用一次色彩空間計算；若首批像素幾乎都不同則停止查表，避免對漸變額外增加查找成本。
工作日誌提交時，模型、圖層與貼圖已在呼叫當下各自取得獨立快照；組裝 `.cbmodel` 內容現在直接使用這些快照，不再為同一筆提交重複深拷貝模型、貼圖組和每層像素來源。一般檔案匯出仍保留原本的防變更拷貝。

- 已把一般與螢幕空間筆畫的原值／覆蓋率快照改成按 64×64 tile 建立，預覽重畫只還原碰到的 tile；連續筆畫保留合併後的滑鼠採樣點，長段繪畫會讓出畫面更新機會。
- 即時繪畫回歸修正：整條三維／螢幕空間筆畫佇列也按時間片讓出畫面更新；貼圖同步優先排主視圖，UV 預覽跟隨主視圖之後刷新，避免持續拖筆時模型畫面一直等到整條佇列完成。
- 已讓圖層合成先建父子索引，避免巢狀組每層重掃全部圖層。
- 已讓局部幾何提交對既有面數的 BVH 做局部重設；面數或拓撲變化以及多次重設後仍會完整重建。
- 已讓平鋪貼圖同一輪更新共用來源像素，避免每個衍生面各讀取整張來源。
- 已讓匯出先確定格式，再只生成選中格式的內容；取消匯出不進行模型烘焙。
- 以上改動通過原始碼檢查、渲染／繪畫、圖層與日誌測試。尚未有實機 GPU 時間與 P95 輸入延遲，因此不宣稱具體加速比例。

### 視角拖動與跨流程檢查（2026-11-02）

- 模型主視圖：網格改為依吸附精度／模型格式建立一次 GPU buffer；輔助線、包圍框線與合併後的物件點資料按幾何／選取／鎖定版本快取。一般不透明及剔除面的「面區分」直接重用合併 mesh，避免每幀排序所有面並展開成新頂點陣列。半透明模型仍保留逐面排序，以維持原本混合順序。
- 修改器：相同實例的範圍資料不再於每次繪製重新串接大量 UID；同一實例的多段範圍共用一次 WebGL 狀態設定，支援時交由 `WEBGL_multi_draw` 合併提交。缺少擴充時仍按原順序繪製。
- 編輯互動與停靠 UI：多選縮放軸向和投影尺寸按選取幾何版本快取；視角輪盤拖動與主視圖拖動一樣每畫面最多提交一次；輪盤線條只在遮擋順序改變時重新排序；一般視圖的螢幕錨定參考圖在單純旋轉／平移相機時不再改寫 DOM。
- 背景工作：主視圖拖動期間暫緩首頁封面離屏渲染、UV 預覽自轉繪製與選區邊框動畫；它們會在拖動結束後繼續。鎖定虛化的懸浮層在拖相機時使用當前完整畫面，不再為同一滑鼠事件額外重繪模型。繪畫模式的空選面集固定引用，避免每幀誤判為選面變更而重建 GPU 緩衝。
- 這些是對熱路徑的實作，已通過源碼、模型、渲染與歷史測試。尚未取得用戶大型專案的實機幀時間，不能宣稱 FPS 提升數字。若仍卡頓，下一步應在該專案量測 GPU 模型 pass、半透明逐面排序、修改器 draw call 和 DOM 疊加層的 P95 時間，再選擇實例化或透明度管線重構。

### 專案檔與底層 CPU 剖析（2026-11-02）

使用使用者提供的 `鸚鵡螺115.cbmodel` **唯讀**剖析，並加入可重跑的 `node scripts/profile-project.mjs <檔案.cbmodel>`。這個樣本有 205 個元素、34 個組、7 個 Shape／曲線，修改器產生 3 個渲染實例；它不能代表所有專案或實機 GPU 負載。

| 項目 | 樣本觀察 | 結論 |
| --- | ---: | --- |
| 壓縮檔與內容 | 4.15 MB；3442 個檔案 | 多數成本藏在歷史而非現有模型 |
| 交易紀錄 | 201 個檔案，解壓後約 33.1 MiB | 每筆重複完整指標、放置與雜湊表；日後應改變更集加週期檢查點 |
| 貼圖差異 | 182 個檔案，約 11.6 MiB | 像素歷史仍是重要的讀寫與壓縮成本 |
| 解包 | 一次執行約 0.35–0.53 秒 | 已在非同步解包中分段回報進度；仍須把歷史解碼與目前狀態開啟分離 |
| 建立模型／序列化 | 約 8–15 ms／4–6 ms | 不應在畫面幀路徑觸發；持久化仍會產生偶發停頓 |
| 修改器 CPU 結果 | 修改前約 50 ms；將八頂點變換合成一次後，同樣本約 24 ms（五次中位數） | 幾何變動時的去重仍是主執行緒熱點；必須維持快取，不可隨視角重算 |

本輪已把舊版對稱節點的載入查找改為索引，把重複 Cube 判定的旋轉矩陣與父組變換移到 Cube 層級，並在同一輪修改器計算中重用 Cube 的世界座標頂點；繪畫爆炸佈局和修改器渲染共用同一輪結果。沒有平鋪貼圖時，圖集重建不再展開全部 Shape。這些改動只消除重複計算，不改存檔或可見結果。

底層剩餘工作以收益與風險排序：先建立編輯器內 CPU/GPU 分段計時，確認主視圖每幀的模型 pass、半透明面排序、修改器提交、SVG 疊加和 UV 預覽各自的 P95；再將撤銷的可見結果改成受影響元素／像素的記憶體變更集，保留磁碟日誌的順序與崩潰恢復；最後把交易紀錄改成差異加檢查點、圖集改穩定配置、Shape 和拾取改真正局部版本。這三項需要格式兼容與跨分支回放驗證，不能在尚未量測 GPU 的情況下聲稱已解決全部卡頓。

## 共同約束與量測

所有方案必須保持像素、UV、正交與透視拾取、透明穿透、面剔除、組與修改器層級、撤銷分支、導出資料相同。不能為了快而丟筆畫採樣點、降低 UV 精度、跳過可見的修改器結果或延後已承諾的畫面反饋。

先建立可重現的五組專案：大量普通 Cube；高細分 Shape／曲線；多層與遮罩的高解析貼圖；多重對稱與拷貝修改器；大量貼圖與圖層的匯入專案。每組記錄冷啟動、開檔、拖動視角、單點／全選、連續繪畫、Ctrl 螢幕空間繪畫、撤銷／重做、模板生成與導出。記錄 P50／P95／P99 的**輸入至首個可見更新**與幀時間，而不只看平均 FPS。

在主執行緒對 `renderScene`、幾何生成、BVH、拾取、圖層合成、圖集更新、UI 重排、序列化、日誌 IPC 分別加 `performance.mark`；在 WebGL 支援時用 `EXT_disjoint_timer_query_webgl2` 量 GPU 各 pass，並記錄 draw call、GPU buffer／texture 上傳位元組、GC 停頓、Canvas `getImageData`／`putImageData` 的面積。計時功能可在一般發行版關閉。

驗收使用雙路比較：同一專案與操作紀錄在舊／新路徑上比對模型資料、貼圖像素、UV、拾取結果與導出；在固定視角、透視／正交、不同透明度與修改器組合下比對渲染截圖。非同步結果必須帶專案與版本戳；過期結果不得覆蓋新狀態。

## 建議實施順序

1. **先量測、再止血**：加統一量測；優先處理畫筆漏筆與輸入至顯示延遲、整張貼圖複製、圖層合成、螢幕空間逐格拾取、撤銷等待。這些直接對應目前最明顯的交互問題。
2. **建立精確失效協議**：用 `ChangeSet` 連接專案資料、主視圖、UV、預覽、圖集、元素列表與日誌。這是後續所有局部更新的前提。
3. **重構幾何與拾取**：Shape 局部結果快取、typed-array mesh arena、每元素 BVH＋實例 TLAS。從「局部修改仍重建全場拾取結構」轉為真正局部更新。
4. **重構像素資料流**：貼圖 tile 快照、圖層樹 tile 合成、穩定圖集 slot、異步持久化。這會讓高解析貼圖和多圖層作品的成本跟實際改動面積，而非整張貼圖面積走。
5. **最後處理冷路徑與 UI**：模板打包、匯入匯出、首頁、色卡、包系統；根據量測選擇要不要再減少 GPU pass。

## 避免的「假優化」

- 不把每次滑鼠事件任意丟掉：這會重現畫筆隨機漏線。可合併已覆蓋 tile，但必須保留掃過的完整線段與最後端點。
- 不把所有掉幀歸因於 mesh：視角移動時靜態 mesh 原本就有快取，必須先區分 GPU pass、UV 預覽與 DOM 疊加層。
- 不只把工作移入 Worker：若每筆仍傳整張貼圖，序列化與複製成本可能更高；先建立 tile／局部資料協議。
- 不只延遲日誌寫入卻放寬崩潰恢復：內存即時撤銷與有序持久化需有明確版本柵欄和關閉等待點。
- 不用降低視覺品質作為默認解法；如果可提供「互動時暫時低品質」，也要是明示的可選模式，而非此計畫的必要條件。
