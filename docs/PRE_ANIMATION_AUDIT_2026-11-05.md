# 动画开发前的结构与性能审查

日期：2026-11-05。结论：现有不透明场景的相机路径已经稳定，但当前的“属性变化 → 重建几何”路径不适合直接用于逐帧动画。建议先完成下面的 P0 改造，再接时间轴、关键帧与插值界面。

本轮新增审查脚本和报告，没有修改运行时实现。下文严格区分已复现的问题、代码可确认的结构风险和待测场景；建议的目标不是已经实现的性能。

后续已实现的改动与复测结果见[第一轮优化记录（2026-11-06）](OPTIMIZATION_2026-11-06.md)。本页保留优化前的数据供对照。

## 1. 方法与范围

- 扫描 `src/` 与 `electron/` 的全部 179 个 JS/CJS/MJS 文件，共 44,808 行、398 条已解析的模块依赖。统计包含翻译表；文件行数不能直接当作运行成本。
- 扫描静态导入、字面量动态导入与字面量 `require`：没有发现循环依赖、未解析的本地模块或 `common/utils` 反向导入界面领域的问题。变量路径、Worker 通信、依赖注入和事件回调不属于这个“无环”结论。
- 隐藏的独立 Electron 窗口运行生成模型和合成贴图；真实应用流程使用临时用户目录。没有打开或修改用户项目，也没有使用电脑控制工具。
- 实际应用的相机测试记录 CPU、GPU、rAF 和输入间隔；独立渲染测试统计 GPU 缓冲更新次数；独立图层测试记录实际像素读回次数与字节数；应用流程测试覆盖撤销、重做和关闭已保存项目。
- 环境：Windows、Electron 38.8.6、Chromium 140；独立渲染画布为 800×600。微基准的提交时间不等于 GPU 完成时间，普通 Canvas 绘制也可能延迟执行。数值不可直接推广到所有设备或用户模型。

## 2. 关键量测

除特别说明外，耗时为本机 CPU 中位数，单位 ms。微基准样本较短，原始报告同时保留 P95、最大值和样本数。

| 场景 | 1000 Cube | 5000 Cube | 解释 |
| --- | ---: | ---: | --- |
| 单个 Cube 的姿态更新与渲染提交 | 0.5 | 1.2 | 只重建选中的小部分，当前路径可用 |
| 整组姿态更新与渲染提交 | 72.9 | 362.0 | 组内几何逐帧重新生成，直接阻碍动画 |
| 八向对称求值，开启去重 | 81.1 | 289.9 | 包含作用域遍历、变体展开与顶点键计算 |
| 八向对称求值，关闭去重 | 42.5 | 146.0 | 去重之外也存在显著求值开销 |
| 不透明相机提交，补测 | 0.1 | 低于本次计时分辨率 | 20 帧中均没有 `bufferData` |
| 透明相机提交，补测 | 18.1 | 88.6 | 20 帧中 19 帧重新上传排序后的面顶点 |
| 项目 `serialize()` | 3.3 | 17.2 | 分别约 0.75 MB、3.77 MB 的文本 |
| 解析项目 JSON | 1.7 | 12.7 | 还不包含对象恢复和界面刷新 |
| 全量对象恢复 | 1.3 | 5.2 | 未包含解析 |
| 复用未改动元素、只恢复一个 Cube | 0.7 | 3.4 | 已有复用有效，但仍有规模相关工作 |
| 含对称结果的射线拾取 | 0.1 | 0.1 | 本次合成场景中不是主要瓶颈 |

真实应用的 1000 Cube 相机测试持续 8 秒：相机帧间隔 P99 为 **17.4 ms**、最大 **32.5 ms**，没有超过 40 ms 的相机间隔；场景 CPU P99 为 3.2 ms、GPU P99 为 6.64 ms，没有运行错误。没有重现此前的固定周期停顿。内部注入输入绕过物理鼠标路径，因此这不是对所有输入设备的保证。

图层和导出补测：

| 场景 | 结果 | 实际工作量 |
| --- | ---: | --- |
| 100 层、256²、每四层一个自定义相加混合，完整合成 | 124.3 ms | Canvas 与像素混合交替 |
| 同一图层栈，只更新 16×16 区域 | 73.0 ms | 每次补丁仍有 50 次 `getImageData`；8 次共读回 400 KiB |
| 20 层、1024²、同样混合，只更新 16×16 | 15.4 ms | 每次 10 次读回；8 次共读回 80 KiB |
| 30 个箱型 UV 网、共用一张 1024² 来源图 | 442 ms，单次样本 | 180 次整图读回，累计 720 MiB |

这里不能再笼统地说“局部合成没做”：局部区域确实生效，问题是大量同步读回、临时 Canvas 和混合管线切换。普通混合的 CPU 提交很低，也不能据此宣称其 GPU 工作免费。

真实应用流程补测：

- 生成 1000 Cube，初始记录尚未完成时立即修改并撤销：首次可见结果约 **6.84 s**；其中队列等待 **6.74 s**。这是未清空初始写入队列的压力场景，不是所有撤销的固定耗时。
- 随后对同一步反复撤销，中间三次约 **87–98 ms**；重做约 **90–115 ms**。等待采用 20 ms 轮询，端到端值带有这个测量精度限制。
- 记录切换阶段中位数约 **74 ms**，JSON 解析 1.4 ms、对象恢复 0.9 ms、界面与渲染调用 13.4 ms。本次大部分撤销时间不是画 mesh。
- 创建并保存含 5 张 1024² 图层的项目，再正常关闭该项目：`layerRasterCache` 仍保留全部 5 张 Canvas，原始 RGBA 数据下限为 **20 MiB**。该数字还不包含 PNG 字符串、图集或驱动资源。

## 3. 动画开发前的 P0

### A. 将动画姿态与文档、基础几何分开

位置：`src/render/webgl-renderer.js:1660`、`:1719`、`:1778`；`src/editor/workspace-coordinator.js:88`、`:123`、`:141`。

当前选中组改变旋转，会进入选中几何重建，重新计算后代顶点、面与相关缓存。GPU 已有 `modelTransform` 和选择预览变换，但没有供多个动画骨骼使用的独立姿态层。继续把每帧采样值写入 `state.project` 再调用 `markDirty/renderAll`，会同时放大几何、UV 预览、属性、对称、封面和存储工作。

建议建立三个明确的数据层：

1. **文档**：Cube、组、Shape、修改器、贴图引用及未来的动画轨道；只记录用户的创作操作。
2. **求值结果**：基础变换、动画采样值、最终世界矩阵、修改器实例和稳定的源对象映射；以时间与修订号为输入，不回写文档。
3. **渲染快照**：基础网格与材质引用、矩阵和实例数据、拾取加速结构；按变更种类更新。

第一阶段可复用现有模型变换和区段绘制，先实现整组只更新矩阵；随后再评估骨骼矩阵表与实例批处理。不要先强制迁移整个渲染后端。

必须保持：主视图绘制和拾取使用同一版姿态；UV 预览仍能读取原始元素；绘画对称继续按原始建模坐标建立关系；暂停或停止播放不会留下被写入文档的姿态。

### B. 透明排序只更新顺序，不重铺顶点

位置：`src/render/webgl-renderer.js:1275`、`:1292`、`:1303`；`src/render/face-order.js`。

当前虽然复用了排序缓存，但视角改变时通常仍需要新顺序。随后 `flatMap(face.vertices)` 生成大数组，再转为 `Float32Array` 并上传完整排序顶点。实测的透明相机路径明显落后于不透明路径。

建议：基础顶点固定；排序结果写入可复用的面／三角形索引缓冲；深度键和排序暂存数组复用。拓扑不变时禁止重传完整面顶点。需要明确 WebGL 索引类型与扩展的容量回退，并验证原有深度、遮挡和镜像绕序。

不能用关掉正确排序、降低透明效果或改成错误的组级近似排序来换取本轮所谓优化。

### C. 修改器需要依赖图和可复用求值计划

位置：`src/model.js:1646`、`:1686`、`:1711`、`:1750`。

当前镜像预览已经复用已有 mesh，这一点应保留。昂贵的是产生实例列表之前的计算：扫描项目与祖先、展开修改器栈、重新生成 Shape Cube、收集原始顶点、对大量坐标生成字符串键。关闭去重仍然很慢，证明只换一种去重哈希不够。

建议分离：

- 基础几何、Shape 参数、层级、修改器参数、材质、姿态各自的修订号。
- 作用域成员与祖先关系索引，基础 Cube 拓扑与顶点签名缓存。
- 修改器栈的求值计划，避免同一帧反复构建相同前缀和祖先结果。
- 去重的空间候选索引与精确确认步骤。保留当前精度规则以及逐轴尺寸符号；不能回退成只比较包围盒或忽略正负形。
- 动画只改变刚体矩阵时，复用基础几何与实例拓扑；确实改变重合关系时仍需及时更新去重，不可通过延迟多帧来隐藏重复体。

### D. 撤销的可见切换不能继续等整个持久化队列

位置：`src/project/journal-controller.js:158`、`:171`、`:391`；`electron/journal-service.cjs:9`。

现在的等待保护了正确的提交与指针顺序，不能直接删除 `await`。但本机已经复现初始写入积压时，撤销被队列挡住数秒；最近一步的普通切换也仍有约 74 ms 的记录切换成本。

建议先设计最近操作的内存状态／差异窗口，将“编辑器当前修订”和“已经持久化的修订”分开。最近撤销可先在 UI 应用可验证的内存结果，存储侧继续按严格顺序提交和确认；超出窗口才进入磁盘恢复路径。像素保留带原值与结果的脏块，不为每步保存整张贴图。

同一项目的操作顺序、分支和强制关闭恢复规则必须保持。当前共用一个日志 Worker，也应把大归档压缩等批量任务从交互恢复任务中隔离；不能随意重排同一项目中的写入。未来的动画播放 tick 不能成为日志操作，只有编辑关键帧等创作动作进入记录。

## 4. P1：内存、图层与离线工作

### 图层资源按项目／资产拥有并释放

位置：`src/common/core/texture-features.js:6`、`:52`；`src/project/tabs-controller.js:234`；`src/texture/asset-controller.js:722`。

全局强引用 `Map<layerUid, raster>` 没有对应的项目关闭清理。关闭项目仅清引用图来源和资产级 blob URL，删除整张贴图也没有释放其图层光栅。单独删除图层已有部分清理，不能代替资产或项目级生命周期。

建议提供统一资源作用域：资产／项目持有的光栅、图集、缩略图、异步任务、播放状态和 URL 都有明确 `dispose`；仍被打开项目或有限历史窗口使用的资源可以固定保留，其余及时释放。跨项目的缓存身份也不应只依赖一个图层 UID。需要验证关闭时仍在解码的图片不能在稍后重新把资源放回缓存。

### 复杂图层合成减少同步读回与临时资源

位置：`src/common/core/texture-features.js:203`；`src/texture/atlas-controller.js:248`。

保留已有脏区域合成、单笔透明度覆盖规则和区域图集上传。下一步应增加混合依赖图和块级缓存：缓存不变的前后层合成结果、组、蒙版与色阶映射结果，只重新计算受影响块及其真实依赖。

自定义混合优先避免 Canvas/GPU 与 CPU 像素之间逐层往返；可比较固定 CPU 光栅块管线和 GPU 混合实现，再选择适合当前效果的方案。若使用 Worker，应传递有界的块与修订号，不得让过期结果覆盖新笔画。最终像素必须与现有混合、透明度锁定和擦除结果一致，实时笔迹不能退回成松手才显示。

### 导出按来源帧缓存一次像素读回

位置：`src/texture/export-raster.js:38`、`src/texture/export-bake.js`。

`paintBoxNet` 在面循环内对来源整图执行 `getImageData`。相同来源帧被不同 UV 网引用时仍重复读回；现有 UV 网去重能减少相同网，但不同网共享一张纹理仍会触发该问题。30 个小网的补测已经读回 720 MiB。

建议为单次导出建立私有的“来源资产＋帧修订 → 只读像素数组”缓存，多个面／UV 网共用。导出结束释放。不得借用编辑器可变画布或全局图层缓存；继续保持平铺、帧最小公倍数、无损 UV、命名空间和源项目不变的规则。大纹理的栅格和编码工作可作为独立离线任务，避免堵塞交互日志 Worker。

### 主线程快照仍有全项目成本

位置：`src/project/journal-controller.js:399`、`:407`；`src/model.js:1115`。

日志磁盘工作已经在 Worker 中，但进入 Worker 前仍在 UI 线程序列化整个项目、复制资产、解析再组装字符串。5000 Cube 的第一次序列化本身中位 17.2 ms，解析约 12.7 ms，尚未计入第二次编码、贴图快照和 IPC。

建议用已知受影响 UID 与字段生成提交载荷；项目根信息、层级、几何、贴图元数据与像素分开。完整快照继续用于检查点与导出，不能把高频动画编辑都变成整项目 JSON 往返。

## 5. 模块与动画接入边界

没有发现字面量模块环，但存在运行时回调耦合：

| 模块 | 当前规模或依赖 |
| --- | --- |
| `screen/events-controller.js` | 约 190 个注入项，1484 行 |
| `screen/context-menus.js` | 约 68 个注入项 |
| `editor/transform-interaction.js` | 约 63 个注入项，1143 行 |
| `app.js` | 75 条模块依赖，1005 行 |
| `model.js` | 2443 行，18 个模块直接依赖 |
| `render/webgl-renderer.js` | 3387 行 |
| `common/core/texture-features.js` | 17 个模块直接依赖，混合了数据关系和 Canvas 光栅工作 |

建议按真实职责继续拆，不要把这些依赖装进一个拥有同样 190 个方法的 service 对象，也不要通过全局事件总线隐藏调用关系。

- `model/`：节点数据与迁移、层级索引、Shape 求值、修改器计划、烘焙、格式交换分别管理。
- `render/`：资源与缓冲、基础几何编译、姿态提交、透明排序、拾取、辅助叠加层分开。
- `screen/`：视口输入、全局快捷键、项目事件、纹理事件、停靠事件分开绑定；继续遵守焦点和文本输入撤销规则。
- 新建独立 `animation/` 领域，包含轨道数据、纯采样、姿态合成、播放时钟；不让界面控件直接驱动 `model.js` 或渲染器的全量重建。
- 建立帧内更新协调：采样 → 求值 → 矩阵／材质更新 → 主视图／必要预览。已有手翻书的独立播放、帧率和显式播放／暂停语义保留。当前手翻书每 rAF 建资产索引并刷新进度 UI，帧切换还会调用图层编辑窗口；未来不能将整套编辑 UI 刷新直接接到骨骼播放时钟。
- 注册表已覆盖模型格式、Shape、修改器、操作器、停靠等，不需要为了“结构统一”重写全部注册表。补上影响范围与缓存失效声明，比新增一个万能注册中心更重要。

## 7. 推荐落地顺序与验收

1. **先建立求值层、修订号和资源生命周期。** 文档、基础几何、姿态、材质与界面选择分开；缓存有所有者；固定一份基准数据集。
2. **完成组姿态提交和透明索引排序。** 1000 Cube／50 个活动组的姿态测试，以 CPU P95 ≤4 ms 为目标；稳定拓扑播放时不重建或重传基础顶点。透明相机路径以 1000 Cube CPU P95 ≤6 ms 为目标，图像和遮挡必须一致。
3. **修改器计划和最近历史窗口。** 不变 Shape 不重复生成；刚体姿态不重新散列全部原始顶点。最近 32 步内的撤销以可见结果 P95 ≤33 ms 为目标，不等待后台大任务，同时通过现有原子写入、分支、贴图差异和强制关闭恢复测试。
4. **处理图层块依赖和私有导出像素缓存。** 局部绘画不触发整资产读回；同一来源帧在一次导出中只解码／读回一次。AA、透明度、混合、蒙版、平铺和对称效果以像素对比验证。
5. **最后接动画数据和界面。** 先用模拟的 60 Hz 姿态源验证前四项，再写时间轴和关键帧。纯播放不改变项目脏标记、历史长度、封面或项目持久化内容。

补充必须通过的场景：停止／暂停／循环与拖时间；播放时选取和拾取；组与对象叠加修改器；负尺寸与面剔除；多项目各自播放；关闭正在解码或播放的项目；连续创建和关闭 20 次后的资源数量回落；大历史待写期间编辑与撤销；导出与交互并行；Worker 失败或软件被强制关闭后恢复。
